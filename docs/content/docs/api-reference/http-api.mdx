---
title: HTTP API
description: Complete HTTP API reference for Herald notification endpoints.
---

Herald exposes a RESTful HTTP API through the Forge framework. When you use the Forge extension, every route is mounted under `/v1` below a configurable base path (default: `/herald`), so providers live at `/herald/v1/providers`. The API covers providers, templates, template versions, sending, the delivery log, the user inbox, preferences and scoped configuration.

All endpoints accept and return JSON. TypeID strings are used as entity identifiers (e.g., `hpvd_01h...` for providers).

Herald doesn't authenticate requests. Protect the routes with `extension.WithAPIMiddleware` (see [Configuration](/docs/concepts/configuration)). That middleware is also what keeps tenants apart: Herald takes `app_id` from the request as given, so your middleware has to bind each caller to the app they're allowed to use.

## App IDs

List routes need `app_id` and answer 400 without it. Their filters and paging parameters are optional, so `GET /herald/v1/providers?app_id=myapp` lists every provider of the app.

By-ID routes (`/providers/:id`, `/templates/:id`, versions, `/messages/:id`, `/inbox/:id`) take `app_id` as an optional query parameter. Leave it out and you mean the `""` app. A row that belongs to another app answers 404, exactly like a row that doesn't exist, so a response never tells you that an ID exists somewhere else.

## Send

### Send Notification

Sends a notification on a single channel.

```
POST /herald/v1/send
```

**Request body:**

```json
{
  "app_id": "myapp",
  "channel": "email",
  "template": "welcome",
  "locale": "en",
  "to": ["alice@example.com"],
  "data": {
    "name": "Alice",
    "app_name": "My App"
  },
  "org_id": "org-acme",
  "user_id": "user-alice",
  "metadata": {
    "source": "signup"
  },
  "async": false
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `app_id` | string | Yes | Application identifier |
| `channel` | string | Yes | Channel type: `email`, `sms`, `push`, `inapp` |
| `to` | string[] | Yes | Recipient addresses |
| `template` | string | No | Template slug (omit to use `subject`/`body` directly) |
| `locale` | string | No | Locale code for template version (defaults to config) |
| `data` | object | No | Template variable data |
| `subject` | string | No | Direct subject (when not using a template) |
| `body` | string | No | Direct body (when not using a template) |
| `org_id` | string | No | Organization ID for scope resolution |
| `user_id` | string | No | User ID for preference checking and scope resolution |
| `env_id` | string | No | Environment ID |
| `metadata` | object | No | User-defined key-value metadata |
| `async` | boolean | No | Whether to send asynchronously |

**Response (200):**

```json
{
  "message_id": "hmsg_01h9xz...",
  "status": "sent",
  "provider_id": "hpvd_01h9xz...",
  "provider_message_id": "4ef7a2c0-...",
  "logged": true
}
```

`provider_id` is always Herald's own provider ID. The ID the vendor handed back, when it gave one, is `provider_message_id`. `logged` is false when the message log couldn't be written; the send still happened. A user who opted out gets `status: "suppressed"` and a message ID, and nothing is sent.

### Multi-Channel Notify

Sends a notification across multiple channels using a template.

```
POST /herald/v1/notify
```

**Request body:**

```json
{
  "app_id": "myapp",
  "template": "order-confirmation",
  "channels": ["email", "inapp"],
  "to": ["alice@example.com"],
  "user_id": "user-alice",
  "data": {
    "name": "Alice",
    "order_id": "ORD-12345"
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `app_id` | string | Yes | Application identifier |
| `template` | string | Yes | Template slug |
| `channels` | string[] | Yes | Channel types to send on |
| `to` | string[] | Yes | Recipient addresses |
| `user_id` | string | No | User ID for preferences and scope |
| `locale` | string | No | Locale code |
| `data` | object | No | Template variable data |
| `org_id` | string | No | Organization ID |
| `env_id` | string | No | Environment ID |
| `metadata` | object | No | User-defined metadata |
| `async` | boolean | No | Whether to send asynchronously |

**Response (200):**

```json
[
  {
    "message_id": "hmsg_01h9xz...",
    "status": "sent",
    "provider_id": "hpvd_01h9xz..."
  },
  {
    "message_id": "hmsg_01h9y0...",
    "status": "sent",
    "provider_id": "hpvd_01h9y0..."
  }
]
```

## Providers

Credential values never come back from the API, whether you create, read or update a provider. Every provider response carries `credentials` as a list of `{key, protection, key_id}`, so you can see which keys are set and whether each one is encrypted (`protection` is `aes-256-gcm` or `plaintext`, and `key_id` names the key that encrypted it).

### Create Provider

```
POST /herald/v1/providers
```

**Request body:**

```json
{
  "app_id": "myapp",
  "name": "SMTP Production",
  "channel": "email",
  "driver": "smtp",
  "credentials": {
    "username": "noreply@example.com",
    "password": "secret"
  },
  "settings": {
    "host": "smtp.example.com",
    "port": "587",
    "from": "noreply@example.com",
    "from_name": "My App"
  },
  "priority": 0,
  "enabled": true
}
```

Herald validates the provider before it stores anything: the driver has to exist and handle the channel, no secret may sit in `settings`, no setting may sit in `credentials`, and the driver's own checks have to pass. When a credential key is configured, credentials are encrypted before they're written.

**Response (201):**

```json
{
  "id": "hpvd_01h9xz...",
  "app_id": "myapp",
  "name": "SMTP Production",
  "channel": "email",
  "driver": "smtp",
  "credentials": [
    {"key": "password", "protection": "aes-256-gcm", "key_id": "k1"},
    {"key": "username", "protection": "aes-256-gcm", "key_id": "k1"}
  ],
  "settings": {"host": "smtp.example.com", "port": "587", "from": "noreply@example.com", "from_name": "My App"},
  "priority": 0,
  "enabled": true,
  "created_at": "2024-01-15T10:30:00Z",
  "updated_at": "2024-01-15T10:30:00Z"
}
```

### List Providers

```
GET /herald/v1/providers?app_id=myapp&channel=email
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `app_id` | query | Yes | Filter by application |
| `channel` | query | No | Filter by channel type |

**Response (200):** Array of provider objects.

### Get Provider

```
GET /herald/v1/providers/:id?app_id=myapp
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `app_id` | query | No | The provider's application. Absent means the `""` app. Another app's provider is a 404. |

**Response (200):** Single provider object.

### Update Provider

```
PUT /herald/v1/providers/:id?app_id=myapp
```

The body is partial. Leave a field out and it stays as it was, so a request without `enabled` doesn't switch the provider off. `credentials` and `settings` merge into what's stored: keys you send are set, keys listed in `remove_credentials` or `remove_settings` are deleted, and everything else is kept. A provider's channel and driver can't change after it's created, so create a new provider for that.

**Request body** (every field optional):

```json
{
  "name": "Updated Name",
  "priority": 1,
  "enabled": false,
  "credentials": {"password": "new-secret"},
  "remove_credentials": ["username"],
  "settings": {"port": "465", "use_tls": "true"},
  "remove_settings": ["from_name"]
}
```

Moving `base_url` or `host` to a new value needs the provider's secret credentials in the same request. Without that rule, anyone who can edit a provider could point it at a server they run and collect the API key or password on the next send. So send the secrets again next to the new target:

```json
{
  "settings": {"host": "smtp.new-vendor.example"},
  "credentials": {"password": "secret"}
}
```

Leave them out and you get a 400 that names the setting and the keys to enter again, and nothing is written. A secret is whatever the driver's schema marks secret. For a driver with no schema, that's every credential. You don't need to send anything again to remove `base_url` or `host` (which puts the vendor's default back) or to set one to the value it already has.

The rule looks at the target the driver actually reads, which is `credentials` merged under `settings`. Putting `base_url` in `credentials`, or removing the setting so a credential copy shows through, doesn't get around it. Connection targets belong in `settings`: Herald answers 400 for `base_url` or `host` in `credentials`, and for any other key the driver's schema places in settings.

**Response (200):** Updated provider object.

### Delete Provider

```
DELETE /herald/v1/providers/:id?app_id=myapp
```

**Response:** 204 No Content.

### Encrypt Stored Credentials

```
POST /herald/v1/providers/encrypt?app_id=myapp
```

Encrypts every plaintext credential of every provider in the app. Turning on a credential key doesn't touch rows that are already stored, so run this once per app after you set the key. A second run changes nothing. Without a configured key it answers 400.

**Response (200):**

```json
{
  "providers": 3,
  "values_encrypted": 5,
  "already_encrypted": 0
}
```

## Templates

### Create Template

```
POST /herald/v1/templates
```

**Request body:**

```json
{
  "app_id": "myapp",
  "slug": "welcome",
  "name": "Welcome Email",
  "channel": "email",
  "category": "transactional",
  "variables": [
    {"name": "name", "type": "string", "required": true},
    {"name": "app_name", "type": "string", "required": false, "default": "My App"}
  ],
  "enabled": true
}
```

**Response (201):** Template object with generated `id` (`htpl_...`).

### List Templates

```
GET /herald/v1/templates?app_id=myapp&channel=email
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `app_id` | query | Yes | Filter by application |
| `channel` | query | No | Filter by channel type |

**Response (200):** Array of template objects.

### Get Template

```
GET /herald/v1/templates/:id
```

**Response (200):** Template object with `versions` array populated.

### Update Template

```
PUT /herald/v1/templates/:id
```

**Request body** (all fields optional):

```json
{
  "name": "Updated Welcome Email",
  "category": "auth",
  "enabled": false
}
```

**Response (200):** Updated template object.

### Delete Template

```
DELETE /herald/v1/templates/:id
```

Deletes the template and all its associated versions.

**Response:** 204 No Content.

```

```

```json
{

```

**Response (201):** Version object with generated `id` (`htpv_...`).

### List Versions

```
GET /herald/v1/templates/:id/versions
```

**Response (200):** Array of version objects for the specified template.

### Update Version

```
PUT /herald/v1/templates/:id/versions/:versionId
```

**Request body** (all fields optional):

```json
{
  "subject": "Updated subject line",
  "html": "<h1>Updated HTML</h1>",
  "active": false
}
```

**Response (200):** Updated version object.

### Delete Version

```
DELETE /herald/v1/templates/:id/versions/:versionId
```

**Response:** 204 No Content.


### Update Preferences

```
PUT /herald/v1/preferences
```

**Request body:**

```json
{
  "app_id": "myapp",
  "user_id": "user-alice",
  "overrides": {
    "marketing-weekly": {
      "email": false,
      "push": true
    }
  }
}
```

The `overrides` map keys are template slugs. Each value is a `ChannelPreference` object with optional boolean fields for `email`, `sms`, `push`, and `inapp`. A `false` value means the user opts out of that channel for that template.

**Response (200):** Updated preference object.

```json
  },

    "id": "hscf_01h9y0...",
    "app_id": "myapp",

    "scope_id": "org-acme",
```

### Set App Config

```
PUT /herald/v1/config/app
```

**Request body:**

```json
{
  "app_id": "myapp",
  "email_provider_id": "hpvd_01h9xz...",
  "sms_provider_id": "hpvd_01h9y0...",
  "push_provider_id": "",
  "from_email": "noreply@myapp.com",
  "from_name": "My App",
  "from_phone": "+15551234567",
  "default_locale": "en"
}
```

A provider ID has to name a provider of the same app, on the channel of the field it sits in (`email_provider_id` takes an email provider, `sms_provider_id` an SMS provider, and so on for `push_provider_id`, `webhook_provider_id` and `chat_provider_id`). Anything else answers 400 and nothing is stored. The same rule applies to org and user configs.

**Response (200):** Scoped config object.

```
PUT /herald/v1/config/org/:orgId
```

**Request body:**

```json
  "from_email": "noreply@acme.com",
  "from_name": "Acme Corp"
}
```

Every provider ID and sender field is optional.

**Response (200):** Scoped config object.

## Error Responses

Errors come back in the Forge framework's standard format:

```json
{
  "code": 400,
  "error": "herald: invalid provider: changing host sends credentials to a new server; enter password again in the same update"
}
```

An error message names keys and IDs. It never contains a credential value.

### Common Error Codes

| Status | Meaning |
|--------|---------|
| 400 | Bad input: a malformed ID, a missing required parameter such as `app_id` on a list route, a provider that fails validation, a routing rule naming a provider it can't use, a template that won't render, or a credential problem (no key configured, a key that isn't configured any more, a stored value that can't be read) |
| 404 | The row doesn't exist, or it belongs to another app |
| 409 | A duplicate: the same template slug and channel in one app, or a second version for the same locale |
| 500 | Anything without a domain meaning, such as a database failure |
