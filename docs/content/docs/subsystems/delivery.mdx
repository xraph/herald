Herald's delivery pipeline is the core of the notification engine. It resolves templates, checks user preferences, selects the right provider through the scope chain, and dispatches messages through the appropriate driver. There are two entry points: `Send` for single-channel delivery and `Notify` for multi-channel template-based delivery.

## Send vs Notify

Herald provides two methods for sending notifications, each suited to different use cases.

### engine.Send()

`Send` delivers a notification on a single channel to one or more recipients. You specify the channel, and optionally a template or raw content:

```go
result, err := h.Send(ctx, &herald.SendRequest{
    AppID:    "app_01abc...",
    Channel:  "email",
    Template: "auth.password-reset",
    To:       []string{"alice@example.com"},
    Data: map[string]any{
        "user_name": "Alice",
        "app_name":  "MyApp",
        "reset_url": "https://myapp.com/reset?token=xyz",
    },
})
```

You can also send without a template by providing `Subject` and `Body` directly:

```go
result, err := h.Send(ctx, &herald.SendRequest{
    AppID:   "app_01abc...",
    Channel: "email",
    To:      []string{"alice@example.com"},
    Subject: "Account Update",
    Body:    "Your account settings have been updated.",
})
```

### engine.Notify()

`Notify` sends a template-based notification across several channels in a single call. Herald iterates over the specified channels and calls `Send` for each one:

```go
results, err := h.Notify(ctx, &herald.NotifyRequest{
    AppID:    "app_01abc...",
    Template: "auth.password-changed",
    Channels: []string{"email", "inapp"},
    To:       []string{"alice@example.com"},
    UserID:   "user_01xyz...",
    Data: map[string]any{
        "user_name": "Alice",
        "app_name":  "MyApp",
    },
})
```

If `Send` returns an error on one channel (no provider, a missing template), Herald logs a warning, adds a `failed` result for it and carries on with the remaining channels. The returned `[]*SendResult` slice contains one result per channel. Each of those is the result for the first address in `To` only (see below).

## Delivery Pipeline Steps

When `Send` is called, Herald executes the following steps in order:

### 1. Preference Check

If a `UserID` and `Template` are provided, Herald checks whether the user has opted out of this notification type on the requested channel:

```go
if req.UserID != "" && req.Template != "" {
    pref, _ := h.store.GetPreference(ctx, req.AppID, req.UserID)
    if pref != nil && pref.IsOptedOut(req.Template, req.Channel) {
        return h.suppress(ctx, req), nil
    }
}
```

If the user has opted out, Herald writes a message row with status `suppressed` for each recipient, records an audit event, and returns a `suppressed` result without calling a driver. See [Preferences](/docs/subsystems/preferences) for details.

### 2. Template Resolution and Rendering

If a `Template` slug is specified and no raw `Body` is provided, Herald looks up the template by slug, app, and channel, then renders it for the requested locale:

```go
tmpl, err := h.store.GetTemplateBySlug(ctx, req.AppID, req.Template, channel)
rendered, err := h.renderer.Render(tmpl, locale, req.Data)
```

The locale falls back through the chain: exact match, language prefix, then default. See [Templates](/docs/subsystems/templates) for the rendering details.

### 3. Provider Resolution

Herald resolves the best provider for the channel using the [scope chain](/docs/subsystems/scoped-config):

```
User scope -> Org scope -> App scope -> Priority-based fallback
```

```go
resolved, err := h.resolver.ResolveProvider(ctx, req.AppID, req.OrgID, req.UserID, channel)
```

The resolver returns both the `Provider` and any `Config` overrides for sender info. (`Config` also has a `DefaultLocale` field, but `Send` doesn't read it: the locale comes from the request or the engine's default.) If no provider is found at any level, Herald returns `ErrNoProviderConfigured`. A request with `ProviderID` set skips the resolver.

### 4. Driver Lookup

Once a provider is resolved, Herald retrieves the corresponding driver from the driver registry:

```go
drv, err := h.drivers.Get(prov.Driver)
```

The driver name on the provider (e.g., `"smtp"`, `"resend"`, `"twilio"`) must match a registered driver. See [Drivers](/docs/subsystems/drivers) for the built-in options.

### 5. Message Construction

Herald builds the outbound message, injecting provider credentials and scoped sender info:

```go
outbound := &driver.OutboundMessage{
    Subject:  rendered.Subject,
    HTML:     rendered.HTML,
    Text:     rendered.Text,
    Title:    rendered.Title,
    Data:     driverData,    // credentials + settings
}

// Sender info from scoped config or provider settings
if resolved.Config != nil {
    outbound.From = resolved.Config.FromEmail
    outbound.FromName = resolved.Config.FromName
}
```

### 6. Delivery and Logging

For each recipient, Herald creates a message log entry, sends via the driver, and updates the status. The code below is simplified:

```go
msg := &message.Message{
    ID:       id.NewMessageID(),
    Status:   message.StatusSending,
    Attempts: 1,
    // ... other fields
}
_ = h.store.CreateMessage(ctx, msg)

result, sendErr := drv.Send(ctx, outbound)

var d message.Delivery
if sendErr != nil {
    d = message.Delivery{Status: message.StatusFailed, Error: sendErr.Error()}
} else {
    sentAt := time.Now().UTC()
    d = message.Delivery{Status: message.StatusSent, SentAt: &sentAt, ProviderMessageID: result.ProviderMessageID}
}
_ = h.store.RecordDelivery(ctx, msg.ID, d)
```

### 7. Inbox Entry (In-App Channel)

When the channel is `inapp`, a `UserID` is provided and the delivery succeeded, Herald also creates an inbox notification entry:

```go
if channel == string(ChannelInApp) && req.UserID != "" {
    _ = h.store.CreateNotification(ctx, &inbox.Notification{
        ID:     id.NewInboxID(),
        UserID: req.UserID,
        Type:   req.Template,
        Title:  rendered.Title,
        Body:   rendered.Text,
        // ...
    })
}
```

## Message Status Lifecycle

Every notification delivery is logged as a `message.Message` record. Messages progress through these states:

```
sending -> sent
        \-> failed
suppressed (opted out, never sent)
```

| Status | Description |
|--------|-------------|
| `queued` | Declared, but nothing sets it today |
| `sending` | Written when the message row is created, before the driver is called |
| `sent` | The driver accepted the message |
| `delivered` | Declared for provider confirmations; nothing records it on a message today |
| `failed` | The driver returned an error (there is one attempt, no retries) |
| `bounced` | Declared, but nothing sets it today |
| `suppressed` | The user opted out, or the device was in quiet hours, so nothing was sent |
| `filtered` | A push fan-out skipped the device because your `DeviceFilter` said no |

```go
const (
    StatusQueued    Status = "queued"
    StatusSending   Status = "sending"
    StatusSent      Status = "sent"
    StatusFailed    Status = "failed"
    StatusBounced   Status = "bounced"
    StatusDelivered Status = "delivered"

    StatusSuppressed Status = "suppressed"
    StatusFiltered   Status = "filtered"
)
```

## Message Entity

The `message.Message` struct captures the full delivery context:

```go
type Message struct {
    ID          id.MessageID      `json:"id"`
    AppID       string            `json:"app_id"`
    EnvID       string            `json:"env_id,omitempty"`
    TemplateID  string            `json:"template_id,omitempty"`
    ProviderID  string            `json:"provider_id,omitempty"`
    Channel     string            `json:"channel"`
    Recipient   string            `json:"recipient"`
    Subject     string            `json:"subject,omitempty"`
    Body        string            `json:"body,omitempty"`
    Status      Status            `json:"status"`
    Error       string            `json:"error,omitempty"`
    Metadata    map[string]string `json:"metadata,omitempty"`
    Async       bool              `json:"async"`
    Attempts    int               `json:"attempts"`
    SentAt      *time.Time        `json:"sent_at,omitempty"`
    DeliveredAt *time.Time        `json:"delivered_at,omitempty"`
    CreatedAt   time.Time         `json:"created_at"`
}
```

Message IDs use the `hmsg` prefix. The `Body` field is truncated to the configured `TruncateBodyAt` limit (default: 4096 characters) to keep the delivery log compact.

## Sync and async

`SendRequest` and `NotifyRequest` have an `Async` flag, but Herald doesn't act on it yet. It's copied onto the message row and that's all. Every send is synchronous: `Send` blocks until the driver returns, and you get the final status back. If you need sends off the request path, run them in your own goroutine or queue.

## Metadata

Both `SendRequest` and `NotifyRequest` accept a `Metadata` map. This is stored alongside the message in the delivery log and on inbox entries, enabling you to attach application-specific context:

```go
Metadata: map[string]string{
    "order_id":   "ord_123",
    "event_type": "order.shipped",
},
```

## SendResult

The return value of `Send` contains the outcome:

```go
type SendResult struct {
    MessageID         id.MessageID   `json:"message_id"`
    Status            message.Status `json:"status"`
    ProviderID        string         `json:"provider_id,omitempty"`
    ProviderMessageID string         `json:"provider_message_id,omitempty"`
    Error             string         `json:"error,omitempty"`
    Logged            bool           `json:"logged"`
    Devices           []DeviceResult `json:"devices,omitempty"`
}
```

`Devices` is only set by a push fan-out. It holds one `DeviceResult` per device, with `DeviceID`, `Status` and `Error`.

`Send` logs one message per address in `To`, but it returns only the first recipient's result. If you pass several addresses and need every outcome, send them one at a time or query the message log. `Logged` is false when the log row couldn't be written; the send still happened.

## Push to a user's devices

A send on the `push` channel with a `UserID` and an empty `To` doesn't go to one address. Herald lists the user's registered devices and delivers to each one the resolved provider can reach, with a message row per device.

```go
result, err := h.Send(ctx, &herald.SendRequest{
    AppID:   "app_01abc...",
    UserID:  "user_01xyz...",
    Channel: "push",
    Subject: "Build finished",
    Body:    "Your deploy went out.",
    Push:    &driver.PushOptions{Urgency: driver.UrgencyTimeSensitive},
    DeviceFilter: func(d *device.Device) bool { return d.Platform == "ios" },
})
```

`DeviceFilter` gives a device it rejects the status `filtered`. A device inside its quiet hours gets `suppressed`, unless the push is `critical` or a withdrawal. A device whose driver answers `driver.ErrAddressGone` is deleted. The overall status is `sent` if any device took the push, else `failed` if any failed, else `suppressed`, else `filtered`, and a user with no devices gets `filtered` with the error `no devices`. A fan-out without a device store returns `herald.ErrNoDeviceStore`. [Devices](/docs/subsystems/devices) has the registry, quiet hours and the push options.

Any push whose rendered title is empty, which includes a raw send with no template, uses `Subject` as the title.

## API Endpoints

The delivery pipeline is exposed through two API routes, under the extension's base path plus `/v1` (for example `/herald/v1/send`):

| Method | Path | Operation |
|--------|------|-----------|
| `POST` | `/send` | Single-channel send |
| `POST` | `/notify` | Multi-channel template-based notify |

The messages delivery log is available for querying:

| Method | Path | Operation |
|--------|------|-----------|
| `GET` | `/messages` | List messages (filter by `app_id`, `channel`, `status`) |
| `GET` | `/messages/:id` | Get a single message |

### Listing Messages

Messages can be filtered and paginated:

```go
type ListOptions struct {
    Channel string
    Status  Status
    Limit   int
    Offset  int
}
```
